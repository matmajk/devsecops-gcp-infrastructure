# JFrog Backing Infrastructure

Terraform module provisioning the Google Cloud backing services required by the JFrog Container Registry deployment.

The module does not deploy JFrog itself. Kubernetes-side bootstrap is handled by Ansible, while the JFrog application lifecycle is managed through Argo CD and Helm.

## Architecture

The JFrog deployment follows the existing platform ownership model:

```text
Terraform
    ↓
GCP backing services
    ├── Cloud SQL PostgreSQL
    ├── GCS filestore
    ├── Secret Manager
    ├── Google Service Account
    └── IAM
         ↓
      Ansible
         ↓
Kubernetes bootstrap and secrets
         ↓
      Argo CD
         ↓
JFrog Helm deployment
```

JFrog runs inside the existing GKE platform but uses external Google Cloud services for persistent data and credentials.

```text
                        Secret Manager
                              │
                              │ Ansible
                              ↓
GKE/JFrog ─────────── Kubernetes Secrets
    │
    ├──────── private VPC ──────── Cloud SQL PostgreSQL
    │
    └──────── Workload Identity ── GCS Filestore
```

## Responsibilities

This module owns:

* JFrog PostgreSQL database infrastructure
* dedicated GCS filestore bucket
* database credentials in Secret Manager
* Secret Manager containers for JFrog master and join keys
* Google Service Account used by the JFrog workload
* IAM access required for the JFrog filestore
* Workload Identity binding for the future Kubernetes ServiceAccount

This module does not manage:

* the `jfrog` Kubernetes namespace
* Kubernetes Secrets
* JFrog master or join key generation
* JFrog Helm installation
* Argo CD Applications or AppProjects
* JFrog repositories and permissions
* CI credentials
* container image promotion

These responsibilities are handled by later Ansible and GitOps stages.

## Resources

The module provisions:

```text
JFrog backing infrastructure
├── Cloud SQL PostgreSQL
│   ├── database instance
│   ├── artifactory database
│   └── artifactory database user
│
├── Secret Manager
│   ├── database password
│   ├── master key container
│   └── join key container
│
├── Cloud Storage
│   └── JFrog filestore bucket
│
└── IAM
    ├── JFrog Google Service Account
    ├── bucket-scoped Storage Admin access
    └── Workload Identity binding
```

## Cloud SQL

JFrog uses an external PostgreSQL database instead of the database bundled with the Helm chart.

The portfolio environment intentionally uses a cost-constrained development profile:

```text
Database:          PostgreSQL 15
Availability:      Zonal
Network access:    Private IP only
Public IPv4:       Disabled
Tier:              db-g1-small
Initial disk:      10 GB
Disk autoresize:   Enabled
Maximum disk:      20 GB
Backups:           Disabled
Deletion protect:  Disabled
```

The instance is reachable through Private Services Access configured by the network module.

```text
      JFrog Pod
          ↓
       GKE VPC
          ↓
Private Services Access
          ↓
 Cloud SQL private IP
```

The database is intentionally not exposed through a public IP.

The following resources are created:

```text
database: artifactory
user:     artifactory
```

The database password is generated by Terraform and stored in Secret Manager.

The password is not exposed through Terraform outputs.

> This configuration is intended for a disposable portfolio environment. A production deployment would normally use larger database capacity, backups, deletion protection and an availability model appropriate for the required SLA.

## GCS Filestore

JFrog binary artifacts are stored in a dedicated Google Cloud Storage bucket.

The bucket uses:

* uniform bucket-level access
* public access prevention
* regional placement matching the platform region
* `STANDARD` storage class
* forced deletion for deterministic portfolio environment teardown

The bucket is dedicated exclusively to JFrog.

The JFrog Google Service Account receives:

```text
roles/storage.admin
```

scoped to the JFrog bucket rather than to the entire GCP project.

This follows the documented JFrog GCS integration model while limiting the IAM blast radius to the dedicated filestore.

## Secret Management

Three Secret Manager resources are provisioned:

```text
<name-prefix>-jfrog-db-password
<name-prefix>-jfrog-master-key
<name-prefix>-jfrog-join-key
```

### Database Password

Terraform:

1. generates the database password
2. configures the Cloud SQL user
3. stores the same value as a Secret Manager secret version

```text
Terraform
    ↓
random database password
    ├── Cloud SQL user
    └── Secret Manager
```

The value is therefore sensitive and is also present in encrypted Terraform state.

Terraform state must be treated as sensitive infrastructure data.

### Master and Join Keys

Terraform creates the Secret Manager containers for:

```text
JFrog master key
JFrog join key
```

but does not create their secret values.

Their lifecycle is delegated to the Ansible bootstrap layer:

```text
Ansible
    ↓
check Secret Manager
    │
    ├── secret version exists
    │             ↓
    │        reuse key
    │
    └── secret version missing
                  ↓
             generate key
                  ↓
              store key
```

This allows the keys to survive GKE recreation while avoiding hardcoded secrets in Terraform or Git.

## Workload Identity

The module creates a dedicated Google Service Account for JFrog.

No long-lived Google Service Account JSON key is generated.

Instead, the infrastructure prepares Workload Identity access for:

```text
Kubernetes namespace:
jfrog

Kubernetes ServiceAccount:
jfrog
```

The binding allows the Kubernetes identity:

```text
jfrog/jfrog
```

to impersonate the dedicated JFrog Google Service Account.

The Kubernetes ServiceAccount itself is created later through the GitOps deployment.

This separation keeps cloud IAM ownership in Terraform while Kubernetes identity remains part of the Kubernetes desired state.

## Security

The JFrog backing infrastructure follows several security controls.

### Private Database

Cloud SQL:

```text
public IPv4 = disabled
```

Database traffic remains on private networking.

### Dedicated Cloud Identity

JFrog receives its own Google Service Account rather than sharing a general-purpose node identity.

### Workload Identity

JFrog authenticates to Google Cloud without a downloaded service account key.

### Bucket-Scoped IAM

`roles/storage.admin` is granted only on the dedicated JFrog filestore bucket.

It is not granted at project level.

### Public Access Prevention

The filestore bucket explicitly prevents public access.

### Secrets Outside Git

Database credentials, master keys and join keys are never committed to the repository or stored directly in Helm values.

## Cost-Constrained Portfolio Profile

The GCP environment runs under Google Cloud Free Trial constraints.

The architecture therefore separates production-like design decisions from portfolio resource sizing.

Production-like patterns retained by the project include:

* external PostgreSQL
* private database networking
* external object storage
* Secret Manager
* Workload Identity
* dedicated workload identity
* GitOps-managed application lifecycle
* infrastructure managed through Terraform

Resource sizing is intentionally reduced for the portfolio environment.

The current environment is designed around an apply-test-destroy lifecycle rather than permanent production operation.

The GKE cluster remains regional, but workloads are planned according to their runtime characteristics:

```text
Permanent / reliability-sensitive
├── GKE system components
├── Argo CD
└── stateful platform services when required

Interruptible / disposable
├── application workloads where appropriate
├── CI runners
├── scanners
└── stateless telemetry components
```

Spot VMs may be introduced for interruption-tolerant workloads, but they are treated as a cost optimization rather than additional Free Trial CPU capacity.

Not all platform tools are expected to run simultaneously.

JFrog, SonarQube and heavier observability components can be enabled according to the milestone being demonstrated while keeping the environment within Free Trial resource constraints.

## Lifecycle

The infrastructure is designed for the portfolio workflow:

```text
  terraform plan
        ↓
  terraform apply
        ↓
platform validation
        ↓
integration testing
        ↓
terraform destroy
```

The JFrog backing resources must therefore support deterministic destruction.

After `terraform apply`, validate:

* Private Services Access
* Cloud SQL private connectivity
* database configuration
* GCS bucket configuration
* Secret Manager resources
* Google Service Account
* IAM bindings

After validation, the environment must also successfully complete a full Terraform destroy.

## Validation

### Cloud SQL

List instances:

```bash
gcloud sql instances list \
  --project=devsecops-portfolio-matmajk
```

Inspect the JFrog instance:

```bash
gcloud sql instances describe <INSTANCE_NAME> \
  --project=devsecops-portfolio-matmajk
```

Verify:

```text
PostgreSQL 15
ZONAL availability
private IP present
public IPv4 absent
```

### Private Services Access

```bash
gcloud services vpc-peerings list \
  --network=<VPC_NAME> \
  --project=devsecops-portfolio-matmajk
```

A Service Networking peering should be present.

### GCS

```bash
gcloud storage buckets describe \
  gs://<JFROG_FILESTORE_BUCKET>
```

Verify:

```text
public access prevention enabled
uniform bucket-level access enabled
```

### Secret Manager

```bash
gcloud secrets list \
  --project=devsecops-portfolio-matmajk \
  --filter="name:jfrog"
```

Expected secrets:

```text
JFrog database password
JFrog master key
JFrog join key
```

The database password should contain an enabled secret version.

Master and join key values are created later by Ansible.

### Google Service Account

```bash
gcloud iam service-accounts list \
  --project=devsecops-portfolio-matmajk \
  --filter="email:jfrog"
```

Verify that the dedicated JFrog identity exists.

### Terraform Lifecycle

Validate both:

```text
terraform apply
```

and:

```text
terraform destroy
```

before considering the module lifecycle validated.
