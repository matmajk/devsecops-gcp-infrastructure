# Project Services

Terraform module responsible for explicitly enabling Google Cloud APIs required by the DevSecOps portfolio platform.

The module defines platform dependencies without attempting to manage every API that Google Cloud may enable automatically for a project.

## Purpose

The module provides an explicit Terraform-managed list of Google Cloud APIs required by the portfolio infrastructure.

This makes service dependencies visible in Infrastructure as Code and ensures that required APIs are enabled before dependent resources are created.

The module does not attempt to make the set of enabled APIs in the project exactly match the Terraform configuration.

Google Cloud enables several platform services automatically when a project is created or when Google Cloud Console features are used. Those platform-managed services are treated as part of the Google Cloud project baseline.

## Responsibilities

The module is responsible for:

* enabling explicitly required Google Cloud APIs
* keeping platform service dependencies visible in Terraform
* preserving enabled APIs during normal portfolio destruction
* exposing the Terraform-managed service list to the portfolio environment

The module is not responsible for:

* disabling Google-managed baseline APIs
* deleting the GCP project
* managing billing
* creating infrastructure that consumes the enabled APIs
* enabling APIs before they are required by the platform

## Managed Services

The portfolio environment currently manages the following APIs:

```text
cloudresourcemanager.googleapis.com
compute.googleapis.com
container.googleapis.com
iam.googleapis.com
logging.googleapis.com
monitoring.googleapis.com
serviceusage.googleapis.com
storage.googleapis.com
```

Additional services are introduced incrementally together with the components that require them.

Examples of services intentionally deferred include:

```text
sqladmin.googleapis.com
servicenetworking.googleapis.com
secretmanager.googleapis.com
dns.googleapis.com
binaryauthorization.googleapis.com
iamcredentials.googleapis.com
sts.googleapis.com
```

This keeps project capabilities aligned with the implemented architecture rather than enabling the complete target platform in advance.

## Lifecycle

Services are managed using `google_project_service`.

The resources use:

```hcl
disable_on_destroy = false
```

This is intentional.

The GCP project exists outside the disposable portfolio Terraform root module and survives normal environment destruction.

The standard lifecycle is therefore:

```text
terraform apply
      │
      ▼
required APIs enabled
      │
      ▼
portfolio infrastructure created
      │
      ▼
terraform destroy
      │
      ├── portfolio resources removed
      │
      └── project APIs remain enabled
```

Enabled APIs do not represent running compute infrastructure and are not removed by the normal portfolio destroy workflow.

## Inputs

| Name         | Type          | Description                                    |
| ------------ | ------------- | ---------------------------------------------- |
| `project_id` | `string`      | Google Cloud project ID where APIs are enabled |
| `services`   | `set(string)` | Google Cloud APIs managed by the module        |

## Outputs

| Name               | Description                                           |
| ------------------ | ----------------------------------------------------- |
| `enabled_services` | Sorted list of Google Cloud APIs managed by Terraform |

## Usage

Example:

```hcl
module "project_services" {
  source = "../../modules/project-services"

  project_id = var.project_id
  services   = local.project_services
}
```

Dependent modules can explicitly wait for project services:

```hcl
module "network" {
  source = "../../modules/network"

  project_id  = var.project_id
  region      = var.region
  name_prefix = local.name_prefix

  subnet_cidr   = var.network_cidrs.subnet
  pods_cidr     = var.network_cidrs.pods
  services_cidr = var.network_cidrs.services

  depends_on = [
    module.project_services
  ]
}
```

This prevents Terraform from attempting to create resources before the corresponding Google Cloud APIs are available.

## Cost Considerations

Enabling an API does not by itself create continuously running infrastructure.

Costs are generated by billable resources or service usage behind an API, such as:

* Compute Engine instances
* GKE clusters and nodes
* Cloud SQL instances
* network traffic
* log ingestion
* persistent storage

Concrete GCP cost assumptions are maintained centrally in [GCP Cost Model](../../../docs/architecture/gcp-cost-model.md).

## Current Status

The module currently establishes the service foundation required for:

* custom VPC networking
* Compute Engine integration
* future GKE deployment
* IAM management
* Cloud Logging
* Cloud Monitoring
* Terraform state storage

Additional APIs will be introduced together with the corresponding infrastructure stages.
